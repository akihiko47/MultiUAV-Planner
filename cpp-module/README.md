# MultiUAV Planner — расчётный MVP, C++17

Модуль принимает существующий PlanRequest и возвращает PlanResponse через прежний
C ABI `char* plan_json(const char*)` / `void free_string(char*)`. Менять backend,
frontend и Docker-конфигурацию для сборки не требуется. Архив поставки содержит
только `cpp-module/**`; исходные файлы остальных каталогов не изменены.

## Быстрый запуск на Windows через существующий Docker

1. Распакуйте `cpp-module-MVP.zip` **в корень вашего репозитория**, согласившись
   заменить файлы внутри `cpp-module`. Вложенность должна быть
   `MultiUAV-Planner/cpp-module/CMakeLists.txt`, без дополнительного cpp-module.
2. Откройте PowerShell в корне репозитория:

```powershell
docker compose up -d --build
curl.exe -f http://localhost:8080/api/health
curl.exe -f -X POST http://localhost:8080/api/v1/plan -H "Content-Type: application/json" --data-binary "@cpp-module/tests/smoke_request.json" -o cpp-module/smoke-result.json
$r = Get-Content cpp-module/smoke-result.json -Raw | ConvertFrom-Json
$r.summary
$r.uav_assignments.Count
$r.uav_assignments[0].waypoints.Count
```

Ожидаются HTTP 200, непустые assignments/waypoints, положительные distance/time,
`uavs_used = 1`. Для этого сценария: 1 вылет и 37 waypoints.
Откройте `http://localhost:8080`; для своих запросов обязательно укажите GSD.
При проблеме: `docker compose logs --tail=100 backend`.

**URL через nginx — `/api/v1/plan`, а не `/v1/plan`.** Префикс `/api`
срезается существующим `frontend/nginx.conf`; backend внутри контейнера слушает
`/v1/plan`. Это расхождение с корневым README здесь учтено, сам README не менялся.

В данной среде Docker Engine отсутствует. Выполнены чистая нативная сборка,
проверка настоящего backend через FastAPI TestClient и проверка запуска только
с libplanner.so без исходного JSON зон. Полный `docker compose build/up` здесь
не запускался; приведённая команда — финальная проверка на вашем ПК.

## Запретные зоны

Основной файл: `cpp-module/no-fly-zons/no_fly_zones.json`. Это побайтовая копия
исходного `frontend/src/data/no_fly_zones.json`: 255 полигонов и 514 окружностей.
Копия имеет **исходный формат Leaflet**: `[latitude, longitude]`. На границе ввода
он явно преобразуется в `[longitude, latitude]`. API и выход всегда используют
GeoJSON `[longitude, latitude]`; `radius_km` переводится в метры.

Порядок загрузки:

1. `PLANNER_NO_FLY_ZONES`, если задан. Ошибка чтения/разбора приводит к отказу;
   незаметного перехода на другую базу в этом случае нет.
2. `cpp-module/no-fly-zons/no_fly_zones.json` относительно рабочего каталога.
3. `no-fly-zons/no_fly_zones.json` относительно рабочего каталога.
4. Абсолютный путь к копии в каталоге исходников, зафиксированный при сборке.
5. Точная копия этого же JSON, встроенная CMake в библиотеку. В ответ добавляется
   предупреждение об использовании встроенной версии.

Последний пункт нужен существующему Dockerfile: он переносит в рабочий образ
только `libplanner.so`. Для обновления базы в штатном Docker-режиме измените файл
**в cpp-module** и пересоберите backend (`docker compose up -d --build backend`).
Frontend автоматически с этой копией не синхронизируется. При отдельном размещении
файла на сервере укажите абсолютный `PLANNER_NO_FLY_ZONES` в окружении процесса.

## Что реализовано

- Проверка чисел, ссылок UAV/type/camera, совместимости камеры, идентификаторов,
  временного окна, простоты колец, положения и пересечения отверстий.
- Polygon с отверстиями. MultiPolygon поддерживается непосредственно C ABI;
  существующий backend его не принимает и возвращает 422 ещё до вызова C++.
- Рабочие параллельные галсы с чередованием направления, обрезкой по внешнему
  контуру и исключением отверстий/запретных зон. Выбор горизонтальной/вертикальной
  ориентации по габаритам. Фрагменты длиной не более 1000 м упрощают деление вылетов.
- Высота из GSD и параметров камеры; ограничение по обеим осям пикселей.
  При меньшей максимальной высоте БВС используется более хорошее GSD. Если для
  заданного GSD требуется высота ниже min_alt, такой БВС не используется.
- Поперечный шаг не больше 49% ширины полосы: запас относительно перекрытия 50%.
  `photo_distance` = половина продольного размера кадра. Ось matrixX считается
  поперечной, matrixY — продольной; фокус/размер матрицы должны иметь одинаковые
  единицы (как в текущем каталоге — мм), GSD приходит в см/пиксель.
- Транзит по графу видимости; отрезки проверяются целиком, не только waypoint-точки.
- При min_turn_radius > 0 — выбор среди шести вариантов Dubins, дискретизация дуг,
  проверка обхода препятствий. Набор/снижение выполняются по винтовой линии с
  ограничением вертикальной скорости; проверяются оба направления вращения.
  При невозможности пробуются альтернативные направления галса и старта.
- При min_turn_radius = 0 и min_speed = 0 используется модель БВС, способного
  зависать: вертикальные набор/снижение, ломаная транзита. Инерция не моделируется.
- Проверка полной 3D длины вылета, расстояния от базы и временного окна. Для
  range/home используется запас 2%; ascent/descent входят в distance и time.
- Несколько вылетов одним БВС с явно заданной паузой обслуживания; после первого
  выбора базы следующие вылеты этого БВС начинаются и заканчиваются на ней же.
- Расписание с точным поиском минимального 3D расстояния на пересекающихся по
  времени линейных участках. Конфликтный вылет сдвигается шагами 5 секунд, затем
  при необходимости — за окончание конфликтующего вылета. Ожидание на земле.
- `min_time`: распределение рабочих фрагментов между БВС с выбором по времени
  завершения на фрагмент; `min_flight_distance`: выбор по длине на фрагмент.
  Маршруты одинаковых UAV/type/camera переиспользуются при оценке кандидатов,
  расписание при этом рассчитывается отдельно для каждого экземпляра.
- Повторная внутренняя проверка всех маршрутов, ограничений и конфликтов до
  сериализации. Независимая Python-проверка использует Shapely, WGS84 Geod из
  pyproj и настоящую backend-модель PlanResponse.

## Метрики и семантика ответа

Каждый элемент `uav_assignments` — **один вылет**. Повторяющийся `uav_id`
означает следующий вылет того же аппарата. `route.coordinates` точно соответствует
последовательности координат `waypoints`; sequence начинается с 0.

- `estimated_distance`: сумма 3D длин выходной ломаной в локальной метрической
  модели, включая вертикальные участки. Независимо проверяется и геодезическая
  длина по эллипсоиду WGS84 относительно лимита аппарата.
- `estimated_time`: от начала взлёта до завершения посадки, в секундах.
- `summary.total_distance`: сумма длин всех вылетов.
- `summary.total_time`: от первого взлёта до последней посадки (makespan),
  **не сумма длительностей параллельных вылетов**.
- `uavs_used`: число уникальных реально использованных UAV, не число вылетов.
- `battery_usage`: `100 * estimated_distance / max_flight_distance`.
  Это доля дальностного ресурса, а не расчёт химического заряда батареи.
- Времена — UTC ISO8601 с миллисекундами. Смещения часового пояса во входе
  нормализуются; время без зоны трактуется как UTC. Если старт отсутствует/null,
  используется текущий UTC и выдаётся предупреждение. При заданном старте
  алгоритм детерминирован.

## Ограничения, которые нельзя скрывать

1. Безопасность проверяется **в описанной геометрической и временной модели**.
   Нет рельефа, ветра, погрешностей навигации/слежения, задержек, динамики
   автопилота, разгона/пробега и препятствий на земле. Высота считается над общей
   плоской поверхностью. Наземное размещение аппаратов на площадке не моделируется.
2. Локальная проекция ограничена радиусом **50 км от первой вершины** и широтами
   **±65°**. Транзит тоже не может выйти за этот предел и за рабочий прямоугольник
   с запасом 10 км. Пересечение антимеридиана зоной съёмки не поддерживается.
3. Невыпуклые запретные полигоны и отверстия заменяются выпуклыми оболочками
   с отступом; окружности консервативно увеличиваются с учётом проекции.
   Отверстия исключаются **также для транзита**. Это может закрывать допустимые
   узкие проходы. Полное покрытие исходной области, занятой такими исключениями,
   не заявляется. Точное объединение полигонов и оптимизация покрытия не реализованы.
4. Галсы строятся по регулярной сетке без отдельного доказательства полного
   покрытия произвольных тонких выступов/фрагментов контура. В отчёте тестов
   приведена геометрическая доля покрытия кадрами для проверенных сценариев;
   она не добавляется в summary, поскольку такого поля нет в API.
5. Эвристика может отказать для математически выполнимой задачи — например,
   из-за ограниченного набора обходов, трёх ближайших баз, направления галсов,
   фиксированного деления на фрагменты или размещения участка набора высоты.
   Отказ не является доказательством невозможности. Частичный план как успешный
   не выдаётся. В исходном `lots_of_holes.json` после добавления GSD=3 план
   для самолётных БВС не найден и возвращается явный отказ.
6. Используются только заданные start_points; новые площадки не выдумываются.
   Вылет возвращается на ту же площадку. Смена базы и подбор разных площадок
   посадки не реализованы.
7. В API нет max_flight_time/ёмкости/расхода батареи или параметров LiDAR.
   `min_voltage` проверяется на корректность, но не превращается в выдуманную
   оценку заряда. RGB/multispectral/Thermal поддерживаются. LiDAR/geophysical
   отклоняются и текущим backend, и C++: нет соответствующего описания датчика.
8. Возврат `{"error":"..."}` сохранён для ошибок. Текущий backend преобразует
   такой ответ в HTTP 500 с общей фразой `Planner call failed`; подробность
   остаётся в серверном логе. Некорректный PlanRequest может получить HTTP 422
   до вызова C++. Эти правила нельзя исправить без изменения backend.
9. Существующий frontend при экспорте Mission Planner ZIP использует только
   uav_id как имя файла: несколько вылетов одного БВС перезаписывают друг друга.
   Для многовылетного плана используйте полный JSON как источник всех заданий.
   Сам exporter также не учитывает расписание вылетов; его нельзя считать
   исполнителем рассчитанного временного разделения.
10. Верхний лимит расчёта по умолчанию 120 секунд, 12 000 рабочих фрагментов,
    500 000 выходных точек и 3000 вершин графа одного поиска обхода. Превышение
    обрабатывается явной ошибкой RESOURCE_LIMIT.

## Конфигурация сервера

JSON-контракт не расширяется. Значения ниже — явно выбранные настройки MVP,
их нужно согласовать с конкретной эксплуатационной моделью.

| Переменная окружения | По умолчанию | Смысл |
|---|---:|---|
| `PLANNER_NO_FLY_ZONES` | не задана | путь к серверному JSON зон |
| `PLANNER_CLEARANCE_M` | 20 | отступ от зон и отверстий, м; минимум 1 |
| `PLANNER_SEPARATION_M` | 30 | минимальное 3D расстояние активных полётов, м |
| `PLANNER_TURNAROUND_SECONDS` | 300 | обслуживание между вылетами одного UAV |
| `PLANNER_MAX_FLIGHT_TIME_SECONDS` | 0 | общий лимит одного вылета; 0 = не задан |
| `PLANNER_CALCULATION_SECONDS` | 120 | лимит вычислений, допустимо 1…1800 |

## Сборка и тесты без Docker

Все C/C++ зависимости находятся в `third_party`; CMake ничего не скачивает.
Требуются компилятор C/C++17 и CMake 3.15+. В Linux:

```bash
cmake -S cpp-module -B cpp-module/build -DCMAKE_BUILD_TYPE=Release
cmake --build cpp-module/build -j 2
cpp-module/build/planner_test cpp-module/tests/smoke_request.json
python3 -m pip install -r cpp-module/tests/requirements.txt
ctest --test-dir cpp-module/build --output-on-failure
python3 cpp-module/tests/integration.py
```

`planner_test` также читает JSON из stdin; stdout содержит только результат.
Код 0 — план, 1 — диагностический JSON отказа, 2 — ошибка чтения/аргументов.
`plan_json(nullptr)` безопасно возвращает error; `free_string(nullptr)` допустим.
Необходимое освобождение строки остаётся ответственностью вызывающего backend.

Sanitizer-сборка (Linux GCC/Clang):

```bash
cmake -S cpp-module -B cpp-module/build-sanitized -DPLANNER_SANITIZERS=ON -DCMAKE_BUILD_TYPE=Debug
cmake --build cpp-module/build-sanitized -j 2
python3 cpp-module/tests/sanitizers.py
```

Сначала выполните основной validator: он создаёт `tests/generated/*`.
Runner отключает LeakSanitizer из-за ptrace-ограничения среды проверки;
AddressSanitizer и UndefinedBehaviorSanitizer включены. Утечки LSan не проверены.
Крупный NFZ-сценарий проверяется Release-валидатором и исключён из debug-прогона,
чтобы не подменять проверку безопасности превышением лимита вычислений.

## Структура

- `planner.cpp`: C ABI, перехват исключений, сериализация PlanResponse.
- `Planner/RequestParser.*`: JSON, ссылки, даты, конфигурация и база зон.
- `Planner/Models.hpp`: независимые от JSON структуры запроса/результата.
- `Planner/Geometry.*`: проекция, проверки колец, исключения, галсы, поиск обхода.
- `Planner/Planner.*`: кинематические переходы, вылеты, распределение и расписание.
- `tests/validate.py`: независимая приёмочная проверка и результаты сценариев.
- `tests/integration.py`: неизменённый backend и встроенная база зон.
- `tests/sanitizers.py`: запуск native CLI под ASan/UBSan.
- `VALIDATION.md`: результаты финального прогона и ограничения проверки.

Лицензии и происхождение включённых библиотек: `third_party/README.md`.
